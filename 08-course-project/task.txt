1. Где взять данные?
Самый удобный вариант для проекта — использовать подготовленный архив на Kaggle, так как официальный сайт BTS часто требует сложной навигации.

Ссылка: Kaggle - Flight Delays and Cancellations

Что внутри: 3 файла (flights.csv, airports.csv, airlines.csv). Основной файл flights.csv содержит данные за весь 2015 год (около 5.8 млн строк).

2. Структура данных (Твой Staging слой)
В файле flights.csv время представлено специфически (например, 1730 вместо 17:30). Твоей первой инженерной задачей в SQL будет превратить это в нормальный TIMESTAMP.

Основные поля для анализа:

YEAR, MONTH, DAY, DAY_OF_WEEK — компоненты даты.

SCHEDULED_DEPARTURE — плановое время.

DEPARTURE_DELAY — задержка вылета в минутах (отрицательное число = вылет раньше срока).

ARRIVAL_DELAY — задержка прилета (самый важный показатель).

CANCELLATION_REASON — причина отмены (A - авиакомпания, B - погода, C - система, D - безопасность).

Ответ Gemini
Отлично! Первый этап Ingestion (загрузка данных) успешно завершен. Теперь у тебя в Google Cloud Storage лежат «сырые» данные, и пришло время превратить их в таблицы BigQuery, с которыми можно работать через SQL.

В рамках проекта мы будем использовать архитектуру Medallion:

Bronze (Raw): Внешние таблицы, которые просто «смотрят» на CSV в бакете.

Silver (Staging): Очищенные данные с правильными типами (например, даты в формате DATE).

Gold (Analytics): Финальные таблицы для дашбордов.

Шаг 1: Создание Внешних таблиц (Bronze Layer)
Поскольку файлы разные (авиакомпании, аэропорты и сами рейсы), нам нужно 3 разных SQL-ассета в Bruin. Начнем с самого простого — справочников.





1. -- Creating an external table to read the airlines lookup file from GCS bucket

CREATE OR REPLACE EXTERNAL TABLE `kestra-sandbox-486404.staging.ext_airlines`
(
  IATA_CODE STRING,
  AIRLINE STRING
)
OPTIONS (
  format = 'CSV',
  uris = ['gs://kestra-zoomcamp-adil-demo/raw/flights/airlines.csv'],
  skip_leading_rows = 1
);


-- Внешняя таблица для Аэропортов
